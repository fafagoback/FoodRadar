# FoodRadar 歷史價格與促銷計算規則

> 與 `PRD.md`、`PROJECT_SPEC.md` 及目前 Python 程式同步（2026-10-28）。

## 唯一正式特價比較：前七天最高有效實質單價 → 本批有效實質單價

- 配對鍵為同一 `store_uuid + product_uuid`。以最新成功批次的有效觀測時間 T 為錨點，取得 `[T-7天,T)` 的有效價格，**取最高值而非中位數、平均值、最低值或上一次價格**。
- `src/price_change.py:PriceChange.seven_day_high` 求七日最高參考價並呼叫 `PriceChange.compare` 計算降幅；`persisted_seven_day` 統一生成 `seven_day_*` 欄位。資料庫版本由 `scripts/repair_effective_prices.py` 依 `products.menu_quote_history` 內營業時段有效觀測建立，前端不重新計算。
- 最新實質單價低於七日最高價就算七日降價；主清單預設 **≥30%**，**無最低省下金額門檻（≥$0）**，且不要求 Uber Eats 有貼促銷標籤。
- 價格維持低價數日仍應列出：100、50、50、50 → 最新 50，前七天最高 100，降 50%。只有當 100 元觀測超出七日時窗、或無法通過當時營業驗證，才不得再作基準。
- 沒有有效七日歷史時，`seven_day_reference_price=NULL`、降幅 0，屬**不可比較**；必須呈現可比較件數與有效採集日期，不得把零結果表述成所有商品沒有特價。
- 只採用當時**實際營業時段**通過 `menu_price_observation_valid()` 的菜單報價；`Delivery unavailable` 本身不排除菜單價比較，必須標示無下單保證。非營業或時間不一致的 RAW 不作主清單基準。

## 前次價格異動是輔助資訊，不能取代七日特價

- `reference_price`、`price_direction`、`is_price_drop`、`price_change_amount`、`price_change_percent`、`discount_amount`、`discount_pct` 描述 **上次有效採集 → 本次** 的單次變價，供詳情頁說明。
- 上次 50、本次 50 可記為持平；但若前七日曾有效記錄 100，`seven_day_discount_pct=50`，**仍須出現在七日特價主清單**。
- `PriceChange.compare` / `qualifies` 是共用的數學與門檻計算方法，`seven_day_high` 才負責選擇七日比較基準。各資料路徑不可自行改用前次價或中位數。

## 實質單價計算規則

所有歷史漲跌、歷史降價幅度、降價 30% 篩選、促銷交叉分類及價格走勢，皆以相同規格的**實質單件成本**計算，不得將上次的商品標價與這次的實質單價直接比較。

- 一般單件：實質單價 = 菜單可支付標價。
- 無促銷多入組：實質單價 = 組合可支付價格 ÷ 件數。
- 買 B 送 F：實質單價 = (菜單每件可支付價格 × B) ÷ (B + F)。
- 第 2 件半價：實質單價 = 菜單單價 × 1.5 ÷ 2。
- 加 1 元多 1 件：實質單價 = (菜單單價 + 1) ÷ 2。
- 平台直接標註 N 折：菜單售價已是折後支付金額，不可再次套用折數。
- 抽取不到有效價格、店家未營業時的不可下單標價：不可用作比較基準。

歷史參考價 `reference_price` 為上一筆經驗證的**實質單價**，而 `products.price` 及 `recent_prices` 仍保留付款標價。資料庫 `effective_price` 與前端單價必須一致。

```text
價格變化百分比 = (本次實質單價 - 上次實質單價) / 上次實質單價 × 100%
降價百分比 = max(0, -價格變化百分比)
每件省下金額 = max(0, 上次實質單價 - 本次實質單價)
```

只有同品項營業時段有效的七日最高歷史實質單價與本次實質單價均有效且本次較便宜時才顯示主清單「七日降價」。降價 30%+ 篩選須與首頁同源。平台促銷標籤屬另一種判斷，兩者可以同時成立，也可以分開成立。

## 具體案例

2026/10/13：鬆餅家「鮮檸冬瓜露」標價 89 元，買 1 送 1，實質單價 44.50 元。

2026/10/21：標價 55 元，無促銷，實質單價 55 元。

結果：單價上漲 10.50 元、漲幅約 23.6%。不是 89 → 55 降價 38.2%，也不是「歷史實質降價」。

## 圖表與畫面顯示

- 歷史圖表的 Y 值必須為**未提前取整**的有效實質單價；歷史表格和卡片採用相同單價定義。
- 金額呈現可遵循 Uber Eats 台灣介面顯示整數元，計算時必須保留至少小數點後 2 位，避免誤差。
- `PRICE_CHANGED` 和 `PROMOTION_CHANGED` 都可能代表實質單價變動。相同採集時間只畫一個點。
- 原始標價與促銷狀態仍需保留，使用者可以理解單價變化原因。
- 修改計算定義後，應從歷史快照重建服務資料庫和查詢索引，不可沿用舊標價導出的 `discount_pct`。


## 最新有效批次才可上架
- **七日降價與目前觀測促銷**必須核對 `product.last_seen == store.last_seen == metadata.latest_processed_at` 且實際營業。**一般商品搜尋**保留最後已知菜單，不要求本批觀測或可配送。
- 最新批次未取得營業時段有效單價，不得出現在**當批七日降價**，但仍可出現在**最後已知菜單目錄**並標示非即時。
- 刪除 36 小時寬限期，使用最新批次觀測而非距離現在的時間來判定。
- 主清單只看本次與前七天最高有效實質單價；前次價格持平不影響七日特價判斷。單次變價欄位仍按本次與前次記錄。
- 過去價格仍留存以供趨勢及下一次有效採集比較，不可用舊資料假裝今天有效。


## 歷史誤判修復（2026-10-27）
- 抓取的原始 JSON 曾出現 `isOpen=true` 同時 `closedMessage="Delivery unavailable"`，舊版誤將其當成已確認可下單價格；重新播放 HF 原始批次時，必須與營業時段菜單報價分開判斷。
- 同 UUID 商品可能同時出現在 `Featured items`、`Buy 1, get 1 free` 及一般分類，須收集所有分類的優惠證據，而非以首次出現為準。
- 舊 `PRICE_CHANGED` 與 `PROMOTION_CHANGED` 事件可能來自不可外送時段；只更新前台篩選不足以修好走勢，必須用新版驗證器對原始快照整庫重建。


## 七日低價主清單規則（2026-10-27）
- 最新有效實質單價相較於本次之前 7 天內最高有效實質單價，降幅達 30% 才列入主清單。
- 從 `menu_quote_history` 中經營業時段驗證、且同 SKU 同批去重的實質單價計算，每一時間點只取一筆實質單價。
- 歷史原價即使僅出現一次，只要有效也可作為七日基準；時間超過七天自然剔除。
- reference_price、price_direction 繼續表示「前次 vs 本次」；seven_day_* 表示七日主清單，前端不能自行重新計算。
- 最新批次沒抓到營業時段有效單價的商品不得進入當批降價索引，但歷史最後菜單仍留在一般搜尋索引。


## HF 原始歷史資料稽核（2026-10-27）
- 截至 2026-10-27 最新成功 Actions，七日內 17 批原始採集批次完成稽核。當批 4,654 項有效商品、其中 964 項有可比較的有效七日歷史價、正式 ≥30% 降價 0 項；另外 2 項舊菜單報價候選，僅可另列參考。先前外送位置未正確帶入 API，造成舊批次大量 `closedMessage`，不可無條件拿來冒充當時可購買的商品價格。
- SQLite 與 Turso 保存通過驗證的有效實質單價；HF 原始 JSON 另行留存，以利追查爬蟲與資料品質。
- 同一 SKU 出現在多個菜單分類時，稽核與匯入都必須合併優惠證據（例如 Featured items + 買一送一），不能因此把同批價格記為一次真漲跌。
- 最新七日降價必須通過實際營業時段的價格驗證；外送可用性獨立標示，非營業時段舊報價不可復活為基準。
- 本次主動重新爬取以建立下一個可信價格觀測；七日資料不足須如實標示，不能虛構降價商品。


## 新增發布安全檢查
- 單店 getStoreV1 必須帶入從 getFeedV1 取得的同一外送座標；缺失時立即回報 FAILED，禁止無座標請求。
- 全批至少 50 家而有效價格為零：中止整批發布，保留先前成功發布的網站資料。
- 白天大量店家同時回傳 Delivery unavailable（>=90% 有關店訊息且有效店家 <5%）：視為疑似外送位置故障，禁止覆寫 HF/Turso。
- 歷史缺口不能憑空補回：已確定不可外送的舊菜單留在 HF Raw 供稽核，不用來偽造可購買的歷史高價。
